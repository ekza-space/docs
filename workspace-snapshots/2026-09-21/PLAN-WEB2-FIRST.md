## Правила для агентов

1. Перед первой записью в любом месте под `/Users/wotori/git/ekza` взять лизу:
   `./agent-lock acquire --agent <имя> ...` (см.
   `_workspace/skills/cross-agent-lock/SKILL.md`). Освободить по завершении.
2. Одна задача из этого плана это одна папка `.agent/tasks/<ID>/` в корне
   umbrella: сначала замороженный `spec.md` с критериями приёмки, потом работа,
   потом `evidence.md` с фактическими результатами команд. Задача закрыта,
   только когда каждый критерий подтверждён на текущем коде. Внутри
   `omoba-bevy` действуют его собственные правила (`CLAUDE.md`, `tasks/`,
   английский язык в документах и коммитах).
3. Ветка на задачу: `feat/<id-в-нижнем-регистре>`. Без push, merge в main,
   деплоя, смены видимости репозитория и удаления файлов вне своей задачи без
   явного согласия основателя. Такие шаги помечены ниже словом «согласие».
4. Код Solana не удалять. Существующие ответы `/api/passport/*`, `/v1/avatars`
   и `/library/avatars` не ломать: поля можно добавлять, нельзя убирать и
   менять смысл.
5. В схеме `studio` прямой доступ к таблицам закрыт. Запись идёт только через
   функции с правами `service_role`: `public.studio_action` (аккаунт, аватары,
   ревизии, публикация; не переписывать без крайней нужды, это обёртка
   ограждения удаляемых аккаунтов) и `public.studio_integration` (игры, профили,
   версии под игру, заявки). Новые действия по интеграции добавляются во вторую.
   Порядок блокировок везде один: аккаунт, аватар, ревизия, версия, заявка.
   Новая таблица со ссылкой на ревизию или профиль обязана каскадно удаляться,
   иначе сломается удаление аккаунта.
6. Задачи одной фазы с разными репозиториями можно вести параллельно. Порядок
   фаз менять нельзя, кроме оговорённого в разделе «Если не успеваем».
7. В конце каждой задачи обновить таблицу статуса и, если изменилось устройство
   системы, `ARCHITECTURE.md` (как система устроена сейчас, включая честный
   список несвязанного). Если меняется цель или статус части, обновить ещё и
   публичную страницу Architecture в репозитории `doc` (без внутренних путей, адресов
   и деталей про платежи и юридические ограничения). В конце фазы ещё и
   `/Users/wotori/git/skills/project-index/references/project-map.md`.

## Исходное состояние (проверено по коду 2026-09-19)

Studio UI:
- Существует только в ветке `feature/avatar-passport-roundtrip` репозитория
  `solana-avatars` (3 коммита впереди main, запушена, main с тех пор не
  двигался). Ветки с тем же именем есть в `core` и `ekza-mirror` (по 1 коммиту).
- Remix 2.16, Vite 6, React 18, Tailwind 3, Node 20+. Файлы:
  `routes/studio.tsx` (1416 строк), `routes/api.studio.$.ts`, `lib/studio*.ts`,
  `components/ui.tsx`, `components/3d/*`, `lib/routes.ts`, `utils/cn`,
  `tailwind.css`. Восемь файлов тестов `tests/studio-*.test.mjs`. Зависит от
  `@ekza/avatar-renderer`, three, R3F. Кода Solana не импортирует.
- Авторизация на стороне сервера приложения: токены лежат в HttpOnly-cookie,
  браузер их не видит, заголовок Authorization из браузера не пересылается,
  для изменяющих запросов проверяется Origin. Обновление токена согласуется в
  памяти процесса, то есть приложение рассчитано на один экземпляр.
- Включается флагом `EKZA_STUDIO_UI_ENABLED`. Без флага `/` и `/studio` ведут
  на `/passport`.

Registry:
- Два независимых источника правды, см. ADR, раздел 11. JSON-каталог отдаёт
  `/v1/avatars` с renditions и `projectSupport`; Studio в Postgres отдаёт
  `/library/avatars` и не знает ни про игры, ни про версии файла под платформу
  (три жёстких слота: `source`, `thumbnail`, `ios`).
- Список проектов зашит в коде как закрытый перечень.
- Studio: таблицы `profiles`, `avatars`, `revisions` (версии есть; статусы
  `draft, queued, processing, review, published, rejected, failed`), `grants`
  (библиотека аккаунта, уже работает), `reviews`, `objects`. Файлы в закрытом
  бакете по ключу `{revision}/{slot}/{sha256}`, отдаются через
  `/v1/studio/assets/{sha256}/{slot}` с мгновенным отзывом.
- Backend оборачивает Supabase Auth своими эндпоинтами `/v1/studio/sessions`
  и т. д. Входа через Google нет.
- `studio_worker` берёт ревизию из очереди, собирает USDZ и отчёт, переводит
  ревизию на проверку.

Omoba и SDK:
- Требования профиля Omoba: GLB, самодостаточный (без внешних `uri`), есть
  skins с суставами, клипы `idle, walk, attack, cast, death`, размер от 20 байт
  до 50 МиБ; исходник обязан быть VRM. Закодированы в
  `omoba-bevy/passport/src/lib.rs` и `omoba-bevy/scripts/ekza_publish.py`.
- SDK и Omoba жёстко требуют идентификатор `solana:devnet:avatar-data:<PDA>` и
  поля `wallet`, `mint` в формате base58.
- Сервер Omoba допускает 15 встроенных аватаров и купленные по тикету
  passport. Бесплатные аватары из registry сервер не допускает вообще, и
  клиента registry на сервере нет.
- Omoba зависит от SDK по закреплённому коммиту из GitHub.

Space (`core`):
- Вход только кошельком, в том числе подпись кошельком при подключении к
  серверу реального времени.
- Профиль Space по коду: `ekza-space / universal / vrm-humanoid-v0|v1`, формат
  VRM 0 или 1, до 50 МБ; анимации `idle` и `walk` даёт движок.
- Уже умеет открыть аватар Studio на предпросмотр по ссылке
  (`?studioAvatar&studioApi`, `spaceLaunchUrl()` в Studio UI).

Mirror:
- В `ekza-mirror` лежат устаревшие копии `backend/`, `deploy/`, `supabase/`.
  Сверка 2026-09-19: совпадают с `ekza-registry`.

## Фаза 4. Заявки, приёмка, единая выдача

**T4.1 Заявки и роль владельца проекта**
Автор отправляет заявку по собранной версии. Владелец проекта видит очередь
своего проекта с отчётом и превью, решает Approve или Reject с причиной.
Общая проверка куратором (безопасность, права) остаётся отдельным шагом до
публикации. Новая ревизия сбрасывает одобрения.
Приёмка: автор видит только свои заявки, владелец только заявки своего
проекта.

**T4.2 Каталог для игр `/v2/avatars`** (в первой редакции плана: единый `/v1/avatars`)
Ответ собирается из двух поставщиков: замороженного JSON-каталога и Postgres.
Аватары Studio получают идентификатор `ekza:avatar:<uuid>`, версии с
`platform / profile / format / sha256 / sizeBytes / downloadUrl`,
`projectSupport` из одобренных заявок. Закрытый перечень проектов в модели
ответа заменяется строкой, проверяемой по таблице проектов.
Приёмка: после Approve аватар виден в `/v1/avatars?platform=desktop&profile=
humanoid-glb-v1` с поддержкой Omoba; после Reject или отзыва не виден;
существующие записи JSON-каталога отдаются без изменений; `/library/avatars`
и Mirror работают как раньше.

## Фаза 5. Магазин и библиотека

**T5.1 Карточка «Работает в»** и фильтр каталога по игре.
**T5.2 «Забрать»**: при цене 0 создаёт запись владения (расширение
существующего `save`); при цене выше 0 кнопка «coming soon». В backend модуль
платёжных провайдеров: интерфейс и единственная реализация для нулевой цены.
Приёмка фазы: гость видит каталог и поддержку игр; после входа забирает аватар;
аватар виден в «Моей библиотеке».

## Фаза 6. Игры

**T6.1 Omoba принимает аватары из каталога** (`ekza-bevy-sdk`, `omoba-bevy`)
SDK: идентификатор принимается по известной схеме (`solana:` или `ekza:`), а не
только `solana:devnet:avatar-data:`. Сервер Omoba получает чтение каталога и
третий исход допуска: аватар бесплатный и одобрен для Omoba, доказательство
владения не нужно. Путь через тикет для купленных остаётся.
Приёмка: аватар, одобренный в T4.1, выбирается в Omoba и виден другим игрокам;
неодобренный и несуществующий идентификатор отклоняются.

**T6.2 Привязка игры к аккаунту**
Registry: выдача кода, страница подтверждения в Studio web, сессия устройства,
`GET /v1/account/library?project=...` из существующей библиотеки. Формат обмена
повторяет привязку passport без полей `wallet` и `mint`. Omoba: группа
«Your Ekza avatars» наполняется из аккаунта.
Приёмка: игрок видит в Omoba ровно то, что забрал в магазине и что одобрено для
Omoba.

**T6.3 Space: предпросмотр и приёмка**
Кнопка «Открыть в Space» в Studio уже есть. Добавить профиль Space, заявку и
одобрение владельцем Space, значок на карточке. Вход аккаунтом Ekza в Space
откладывается: он требует авторизации на сервере реального времени.

## Фаза 7. Демо

**T7.1 Сценарий** от начала до конца локально: скрипт показа, подготовленные
данные (два годных CC0-аватара и один негодный для отчёта), запасная видеозапись.
**T7.2 Прогон** с Google-входом под VPN на том же ноутбуке.

## Стабилизация после ревью 2026-09-21

Локально реализованы: полный ответ v2 либо 503; SDK без потери сохранённого каталога;
выбор версии каждой игрой и сохранение прежнего файла до новой приёмки; отзыв без
автоматического возврата старого одобрения; изоляция двух обработчиков Studio в Docker.
Существующие проверки и новые регрессии: `.agent/tasks/EKZA-STABILIZATION-20260921/`.
Общий Supabase и production не изменялись. Исторические критерии выше, требующие
исчезновения аватара при каждой новой публикации, заменены ADR 0002.

Очередь выпуска: `ekza-registry/docs/stabilization-release.md`. До публичной активации
нужны образ Blender/USDZ, проверка Auth/Storage на полном стенде, выпуск SDK с обновлением
зависимостей игры и визуальный прогон Omoba. Аккаунтный путь Space теперь реализован
локально (см. следующий раздел); далее — его выпуск и самостоятельное прохождение
автором и внешней игрой. Это незавершённые этапы, а не
результат локальной SQL-проверки.

## Space: аккаунтный путь, локальная реализация 2026-09-21

Выполнен следующий после стабилизации этап: каталог выбранных Space-версий,
вход без кошелька с отдельным разрешением `space-session`, библиотека,
серверная проверка equip и контроль файла у каждого клиента, восстановление
после перезагрузки, отзыв/обработка недоступности. Legacy library-токены
не становятся токенами входа, права редактирования сцены остаются за кошельком.

Проверены SQL, HTTP-контракты, TypeScript/Rust и настоящий realtime-сервер
с двумя клиентами на изолированных Registry/RPC fixtures; браузером —
реальный VRM, вход/библиотека/перезагрузка/выход и узкий экран.
Production не менялся. Перед выпуском нужны реальный тестовый Studio-круг,
выпуск SDK вместо локальной file-ссылки и проверка чистой установки renderer.
Подробная приёмка и ограничения: `core/docs/space-account-migration.md`.
