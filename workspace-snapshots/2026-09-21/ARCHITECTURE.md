## Идея в одном абзаце

Автор выкладывает аватар один раз. Каждая игра объявляет, каким должен быть файл
(профиль версии). Registry собирает под профиль отдельный файл (версию), автор
подаёт его в игру, владелец игры одобряет. Игрок забирает аватар в свою
библиотеку и видит его в каждой игре, которая его одобрила. Основной путь идёт
без кошелька; Solana остаётся необязательным слоем.

## Кто где живёт

| Часть | Репозиторий | Роль |
| --- | --- | --- |
| Registry backend | `ekza-registry/backend` (FastAPI) | Каталог для игр, Studio API, профили, версии, заявки, библиотека аккаунта, коммерция |
| Studio web | `ekza-registry/web` (Remix) | Интерфейс для автора, куратора, владельца игры и покупателя. Ходит в backend только по HTTP через серверный прокси, токены в HttpOnly-cookie |
| База и файлы | Supabase: Postgres, Auth, закрытый Storage | Единственный источник правды для всего нового |
| Воркеры | `python -m app.studio_cli worker` | Две очереди в Postgres: обработка ревизии (USDZ для iOS), затем сборка версий под профили |
| SDK для игр | `ekza-bevy-sdk` (Rust), `ekza-stellar-sdk` (TypeScript) | Чтение каталога, скачивание с проверкой хэша и размера, привязка устройства |
| Omoba | `omoba-bevy` | Игра, потребитель протокола. Владеет профилем `desktop / humanoid-glb-v1` и его сборщиком |
| Ekza Space | `core` | Веб-мир, потребитель. Профиль `universal / vrm-humanoid-v1` |
| Ekza Mirror | `ekza-mirror` | iOS-приложение, потребитель. Профиль `ios / arkit-body-v1` |
| Слой Solana | `solana-avatars` (программы, витрина кошелька, API passport), `solana-stellar` | Необязательный слой: NFT-шаблоны, покупка через кошелёк, привязка кошелька в Omoba и Mirror. Заморожен по функциям |
| Stellar | `ekza-stellar` | Заморожен. Командная разработка ассетов переедет в Studio |

## Модель данных (Postgres, схема `studio`)

```
profiles ─┬─ avatars ── revisions ─┬─ renditions ── submissions ── projects
          │   (автор)   (версии      │  (файл под      (заявка в       │
          │              загрузки)   │   профиль)       игру)          │
          ├─ grants (библиотека аккаунта)                 project_members (владельцы)
          └─ project_members                              project_accepts ── rendition_profiles
```

- `revisions`: жизненный цикл `draft → queued → processing → review → published`
  (либо `rejected`, `failed`). Публикует куратор. Текущая опубликованная ревизия
  записана в `avatars.current_revision_id`.
- `rendition_profiles`: селектор `platform / profile` с версией, документом
  требований (`source`, `rendition`) и именем сборщика. Профиль принадлежит
  протоколу: игра его принимает (`project_accepts`). Вторая игра, принявшая тот же
  профиль, сразу совместима с уже собранными версиями.
- `renditions`: одна на пару «ревизия, профиль». `origin = source`, если игре
  отдаётся сама загрузка, `built`, если файл собрал сборщик. Очередь сборки с
  захватом по токену и истекающей арендой.
- `submissions`: заявка версии в проект. Решает только владелец этого проекта.
- `project_releases`: выбранный файл на пару «аватар, игра, профиль». Новая
  публикация сама по себе его не меняет. `active_project_releases` применяет
  единые условия доступности для каталога, скачивания и библиотеки.
- Слот `ios_*` в `revisions` оставлен ради Mirror; представление
  `all_renditions` показывает его как версию `ios / arkit-body-v1`.
- Цена, доли автора, продажи, выплаты живут в схеме `commerce` как условия
  принятого соглашения. На аватаре их нет намеренно.

Правила доступа исполняются в базе, а не в Python. Прямого доступа к таблицам нет
ни у кого, кроме `service_role`. Три функции:
`public.studio_action` (аккаунт, аватары, ревизии, публикация, удаление аккаунта),
`public.studio_integration` (проекты, профили, версии, заявки),
`public.studio_submission_access` (чтение файлов одной заявки).
Порядок блокировок везде один: аккаунт, аватар, ревизия, версия, заявка. Новые
таблицы со ссылкой на ревизию или профиль удаляются каскадно, иначе сломается
удаление аккаунта.

## Главное правило одобрения

Игра использует выбранную ею опубликованную версию. Публикация новой ревизии
не убирает прежнюю: переход происходит после приёмки новой версии этой игрой.
Игры могут одновременно использовать разные ревизии одного аватара.
Отзыв выбранной заявки убирает доступ без возврата к предыдущим одобрениям.
Снятие аватара с публикации и удаление аккаунта скрывают все его версии.
Mirror пока сохраняет прежнее правило: текущая опубликованная iOS-версия.
Причины и границы решения: `adr/0002-approved-revision-continuity.md`.

## Сборщики: игра владеет своими правилами

Профиль называет сборщик. `none` означает, что игре отдаётся сама загрузка
(Space берёт VRM как есть). Иначе это внешняя команда из репозитория игры,
заданная оператором: `EKZA_RENDITION_BUILDER_<ИМЯ>`. Registry запускает её в одноразовом Docker-контейнере без сети, с неизменяемым
корнем, исходником и каталогами кода только для чтения; запись разрешена в папку
текущей попытки. Образ закреплён по digest и заранее установлен оператором.
Без настройки изоляции сборка завершается ошибкой. Затем Registry проверяет путь, хэш,
размер и требования профиля (`app/services/profile_checks.py`). Сборщику не
доверяют на слово. Подключение новой игры не требует правки registry: профиль это
строка в базе, сборщик это команда в настройках.

Контракт команды: `--source <файл> --output-dir <папка>`, один JSON в stdout,
код 0 при успехе, код 2 со списком проблем, если аватар нельзя превратить в версию.
Сборщик Omoba: `omoba-bevy/scripts/ekza_build_rendition.py`, чистый Python,
VRM в GLB с пятью клипами за доли секунды. Сборка USDZ для iOS идёт старым
конвейером обработки ревизии и требует Blender.

## Потоки

Автор: вход → загрузка VRM → `validate` по профилю (что мешает) → отправка на
обработку → куратор публикует → запрос версии под профиль → воркер собирает →
заявка в игру → владелец игры смотрит превью и файл, одобряет.

Владелец игры: раздел «Games» → очередь своей игры → закрытая миниатюра и 3D-просмотр
ровно того файла, что собран → Approve или Decline с заметкой.

Игра: новый код читает `GET /v2/avatars?project=<игра>&platform=&profile=` и получает
только выбранные этой игрой версии, с абсолютной ссылкой, хэшем и размером.
При недоступности Studio ответ 503: неполный каталог нельзя принять за отзыв.
SDK сохраняет последний полный каталог и переходит на `/v1` только при 404 `/v2`. Файл версии
отдаётся анонимно по `/v1/studio/assets/{sha256}/rendition`, отзыв мгновенный.
Каждая запись несёт `access`: `free` (игра допускает без доказательства владения) или
`owned` (нужен тикет passport). Старые клиенты продолжают читать `/v1/avatars` (только
шаблоны Solana) и `/library/avatars`; оба ответа не менялись.

Omoba (SDK 0.6.0) уже читает `/v2`. Сервер игры сам читает реестр и допускает вход без
тикета только для slug, помеченного бесплатным; клиент объявить аватар бесплатным не
может. Slug это хэш идентификатора и хэша файла. При следующем входе известный аватар перепроверяется, если прошло
5 минут после чтения каталога; фонового отзыва модели в текущем матче нет, при недоступном реестре уже одобренное продолжает работать. Купленные аватары
по-прежнему требуют тикет. Mirror на `/v2` не переведён. Для Space реализован локальный переход: серверный
каталог, аккаунтный вход, библиотека и проверенная передача VRM между игроками; выпуск ожидается.

Игрок: в магазине Studio жмёт «Save to my library» (строка в `grants`). В игре жмёт
«Connect Ekza account»: игра показывает короткий код и открывает Studio, человек входит и
подтверждает, игра получает токен и читает `GET /v1/account/library`: то, что аккаунт
сохранил или создал, опубликовано и одобрено для этой игры. В Omoba это группа «My Ekza
library», перечитывается раз в 15 секунд. Привязка ничего не выдаёт: допуск в матч решает
сервер игры по своему чтению реестра. Код устройства и токен генерирует backend, в базе
только их SHA-256; код живёт 10 минут и срабатывает раз, токен 30 дней, отзывается в
разделе Account. Привязка через кошелёк (API passport) работает как раньше, для купленных.

## HTTP-контракты

| Контракт | Кто читает | Состояние |
| --- | --- | --- |
| `GET /v1/avatars`, `/v1/assets/*` | старые SDK, passport, Mirror | Работает, только JSON-каталог шаблонов Solana, неизменяемый снимок. Не менять |
| `GET /v2/avatars` | новые клиенты игр | Работает: оба источника, фильтр по игре и версии, без кэша |
| `GET /v1/studio/assets/{sha}/rendition` | игры | Файл активного одобрения, включая выбранную старую ревизию |
| `GET /v1/studio/assets/{sha}/rendition-thumbnail` | игры | Превью текущей или выбранной игрой ревизии |
| `GET /library/avatars` | Mirror, SDK | Работает, менять нельзя |
| `GET /v1/profiles[/{platform}/{profile}]` | игры, инструменты авторов | Работает, открыт всем |
| `/v1/studio/*` | Studio web | Работает: аккаунт, аватары, ревизии, библиотека, проекты, профили, проверка по профилю, версии, заявки, очередь владельца, файлы заявки |
| `/v1/account/device`, `/device/poll`, `/library` | игры (SDK 0.6.0, Omoba) | Работает: привязка к аккаунту без кошелька, библиотека для одной игры |
| `POST /v1/account/session` | сервер Space | Локально реализовано: только явный scope `space-session`; старые library-токены не подходят |
| `/api/passport/*` (в `solana-avatars/app`) | Omoba, Mirror, Space | Работает, только кошелёк. Не менять до фазы 6 |

Идентификаторы аватара: `solana:devnet:avatar-data:<PDA>` (шаблоны Solana) и
`ekza:avatar:<uuid>` (Studio, виден в `/v2/avatars`). SDK 0.5.0 и Omoba принимают оба.

## Что ещё не связано (честный список)

1. Экраны Studio для игр есть и пройдены в браузере. Мелочи: в 3D-просмотре нет
   кнопки клипа `cast`; блок «Games» делает два запроса на карточку.
2. Цикл «выложил, одобрен, сыгран» замкнут для Omoba и проверен на настоящем сервере по
   сети. В окне игры (группа в выборе аватара, модель на экране) не проверялся.
3. Роль игрока замкнута для Omoba и пройдена настоящим SDK и браузером. В окне игры
   (кнопка, строки статуса, группа «My Ekza library») не смотрелось. Токен игры живёт в
   памяти, после перезапуска привязка повторяется.
4. Space: новый аккаунтный путь реализован и проверен локально. Он требует
   согласованного выпуска Registry/Studio, SDK, realtime-сервера и клиента.
   Подробности: `core/docs/space-account-migration.md`. Предпросмотр Studio остаётся отдельным.
5. Входа через Google нет (T2.1). Платежей нет, в интерфейсе «coming soon».
6. Проверка сборщика Omoba идёт питоновской копией правил игры, а не функцией на
   Rust; тест на совпадение запланирован (T3.5).
7. Боевое окружение не обновлялось. Последние изменения Space и стабилизации
   проверены локально; их миграции не применялись к общей базе.
